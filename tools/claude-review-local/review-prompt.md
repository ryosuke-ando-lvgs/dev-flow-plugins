## 出力形式（厳守）

他の前置き・後書きは一切書かず、必ず以下の形式の `json` フェンス付きブロック**のみ**を
出力してください（ブロックの前後に説明文やコメントを一切書かない）。

```json
{
  "action": "approve|comment|request-changes",
  "body": "## 観点別レビュー\n\n### <観点の見出し>\n- [critical|high|mid|low] <ファイル:行 → 問題点 → 提案>\n（指摘がなければ「問題なし」と一言でよいが、必ず書く）\n\n## 総評\n<1〜3文でPR全体の結論>",
  "findings": [
    {"file": "diff上のファイルパス（例: src/foo.ts）", "line": 42, "severity": "critical|high|mid|low", "message": "指摘内容"}
  ]
}
```

- `action`: 判定結果。
  - `critical`/`high` の指摘が1つでもある → `request-changes`
  - `mid`/`low` の指摘のみ（マージ自体は妨げない） → `comment`
  - 問題なし → `approve`
- `body`: 人間向けの総評コメント本文（Markdown）。JSON文字列として1つのフィールドに
  入れるため、改行は `\n`、ダブルクォートは `\"` のように**正しくJSONエスケープする**こと。
  出力全体が有効なJSONとしてパース可能であることを最優先する。
  - 上記チェックリストに列挙された観点ごとに `###` セクションを作り、それぞれ何を
    確認したか（結果が「問題なし」であっても）必ず明記する。これにより、レビューが
    各観点を実際にチェックした上での判断であることが分かるようにする。
  - ただしPRの内容に明らかに関係しない観点（例: 依存パッケージ更新でないPRにおける
    「依存パッケージ更新のレビュー」観点）は、そのセクション自体を省略してよい。
  - 「要件との整合性確認」観点（`checklists/01-requirements-consistency.md`）だけは
    例外で、PRの内容によらず**必ず出力する**（省略不可）。
  - 個々の指摘には、行頭に `[critical]` `[high]` `[mid]` `[low]` のいずれかを必ず
    付ける（「問題なし」の場合はタグ不要）。目安:
    - `critical`: 本番で確実に壊れる・データ破損/セキュリティ侵害につながる・
      要件を満たしていない
    - `high`: 特定条件下でバグや重大な劣化を引き起こしうる
    - `mid`: 保守性・設計・パフォーマンス上の軽微〜中程度の懸念（即座の不具合ではない）
    - `low`: 命名・コメント・スタイル等の些細な指摘
  - 誇張・断定しすぎない。確信度が低い指摘は「〜の可能性があります」と書く。
- `findings`: diff上の特定のファイル:行に紐づく指摘だけを機械可読な形でも列挙する配列。
  レビューシステムがこれを各行へのインラインコメントとして投稿するために使う
  （`body` には含まれない、GitHub Reviews API の行コメント専用の情報）。
  - `file` は diff の `+++ b/...` に現れるリポジトリルートからの相対パス、`line` は
    diff の新しい方（追加後）のファイルにおける行番号（対象行がdiffの変更/追加範囲に
    含まれている必要がある。diffに含まれない行は指定できない）。
  - `body` 中で挙げた指摘のうち、具体的なファイル:行に紐づくものだけをここにも列挙する。
    ファイル横断的な指摘や一般論はここに含めなくてよい。
  - 該当する指摘が無い場合は空配列 `[]` を出力する。省略はしない。
